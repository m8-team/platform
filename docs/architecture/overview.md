# Обзор архитектуры

M8 Platform организована как монорепозиторий с backend на Go, будущей веб-консолью, API-контрактами и инфраструктурой. На текущем этапе существует только каркас.

## Размещение компонентов

| Область | Назначение |
| --- | --- |
| `cmd/resource-manager/`, `cmd/identity/`, `cmd/authentication/`, `cmd/access/` | Место для будущих точек запуска |
| `internal/resource/domain/` | Предметные правила Resource Manager |
| `internal/resource/application/` | Сценарии приложения Resource Manager |
| `internal/resource/adapters/` | Адаптеры внешних зависимостей Resource Manager |
| `internal/resource/transport/` | Транспортные адаптеры Resource Manager |
| `internal/identity/`, `internal/authentication/`, `internal/access/` | Будущая реализация остальных модулей |
| `internal/platform/app/` | Общие механизмы запуска приложения |
| `internal/platform/telemetry/` | Общие механизмы наблюдаемости |
| `internal/platform/messaging/` | Место для механизмов обмена сообщениями, если они потребуются |
| `api/proto/m8/` | Контракты модулей и событий |
| `migrations/resource-manager/`, `migrations/identity/` | Место для будущих миграций |
| `web/apps/console/` | Будущая веб-консоль |
| `web/packages/ui/`, `web/packages/module-sdk/` | Место для общих UI-компонентов и SDK модулей |
| `deploy/helm/`, `deploy/environments/` | Место для будущих описаний поставки и окружений |

Для будущего кода Resource Manager предметный слой должен оставаться независимым от транспорта и конкретных внешних технологий; сценарии приложения используют предметные правила, адаптеры связывают их с внешней средой. Общие технические компоненты не должны становиться местом хранения предметных правил модулей.

Существование `cmd/` не утверждает независимое развёртывание четырёх сервисов. Каталоги `messaging/`, `events/v1/`, `migrations/` и `helm/` не утверждают выбор брокера, событийной модели, СУБД или целевой платформы развёртывания. `v1/` резервирует пространство имён, но не означает опубликованный контракт.

## Что предстоит решить

Исходное распределение ответственности и открытые интеграции описаны в [границах модулей](module-boundaries.md). До реализации соответствующей функции требуется уточнить:

- модель арендатора, иерархию ресурсов и владение данными;
- вызовы между модулями, контракты, обработку сбоев и требования согласованности;
- хранение, транзакционные границы и жизненные циклы данных;
- способы аутентификации и модель разрешений;
- Go module path, версию Go, необходимые зависимости и проверки;
- при появлении соответствующей задачи — веб-стек и топологию поставки.

Значимые решения оформляются по [правилам ADR](../adr/README.md). Принятые решения перечислены в реестре ADR.
