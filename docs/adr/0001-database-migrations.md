# `ADR-0001`: Система миграций базы данных

- Идентификатор: `ADR-0001`.
- Дата: `2026-09-19`.
- Статус: `Accepted`.
- Подтверждение согласования: решение владельца проекта от `2026-09-19` — выбрать `pressly/goose/v3`; зафиксировано в commit [`4c256b0`](https://github.com/m8-team/platform/commit/4c256b024f719d4e4196af3b42b9eab74bf20259).

## Контекст

M8 Platform требуется единый механизм версионирования и применения изменений схемы базы данных. В репозитории уже зарезервированы каталоги `migrations/resource-manager/` и `migrations/identity/`; до принятия этого ADR единый инструмент миграций не был выбран.

Инструмент должен:

- подходить для backend-проекта на Go и использоваться как CLI и/или Go-библиотека;
- поддерживать SQL-миграции и хранить состояние применённых миграций в базе данных;
- обеспечивать команды для применения, отката, проверки статуса и валидации миграций;
- не требовать отдельного JVM toolchain без существенной причины;
- иметь поддержку YDB, если YDB будет выбрана отдельным архитектурным решением;
- оставлять миграции читаемыми и переносимыми между локальной разработкой, CI и окружениями;
- не связывать выбор инструмента миграций с окончательным выбором СУБД.

Этот ADR выбирает механизм управления миграциями, но не выбирает СУБД. Если будущий ADR по хранилищу выберет СУБД, которую выбранный инструмент не поддерживает удовлетворительно, это решение должно быть пересмотрено.

При оценке использован установленный skill `ydb-core` для проверки особенностей и существующих интеграций YDB.

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения и последствия |
| --- | --- | --- |
| [pressly/goose v3](https://github.com/pressly/goose) | Go-native CLI и библиотека; SQL- и Go-миграции; upstream поддерживает YDB и другие распространённые СУБД; есть `up`, `down`, `status`, `validate`; YDB документирует goose как поддерживаемый инструмент миграций. | Формат SQL-файлов содержит директивы goose; Go-миграции могут увеличить связанность миграций с кодом; особенности DDL конкретной СУБД всё равно остаются в самих миграциях. |
| [Flyway](https://github.com/flyway/flyway) | Зрелая модель версионированных миграций; YDB имеет официальный dialect и документацию; развитые команды проверки и восстановления состояния. | Добавляет Java/JDBC toolchain в Go-проект; YDB требует отдельный dialect и JDBC driver; усложняет локальную среду и CI относительно Go-native решения. |
| [Liquibase](https://github.com/liquibase/liquibase) | Зрелый инструмент, декларативные changelog-форматы, развитая экосистема; YDB имеет официальную интеграцию. | JVM/JDBC toolchain; более сложная модель changelog, чем требуется для текущего проекта; декларативные абстракции могут скрывать реальные особенности YDB/YQL. |
| [golang-migrate/migrate](https://github.com/golang-migrate/migrate) | Простой формат `up/down`, Go-native CLI и библиотека, широкое распространение. | На дату ADR поддержка YDB ещё не находится в стабильном upstream: PR [#1215](https://github.com/golang-migrate/migrate/pull/1215) остаётся открытым; YDB поддерживается отдельным fork `ydb-platform/golang-migrate`, что создаёт дополнительный риск сопровождения. |
| Собственные migration scripts | Полный контроль и отсутствие зависимости от внешнего migration framework. | Потребуется самостоятельно реализовать версионирование, блокировки, статус, повторный запуск, восстановление после ошибок и tooling для CI; высокая стоимость поддержки без уникальной выгоды. |

## Решение и обоснование

Используется **`pressly/goose/v3`** как стандартный механизм миграций M8 Platform.

Основные причины:

1. **Соответствие Go-стеку.** Goose реализован на Go, доступен как CLI и библиотека и не требует JVM/JDBC toolchain.
2. **Поддержка YDB в основном upstream.** Текущий upstream goose включает драйвер YDB, а документация YDB содержит отдельное руководство по использованию goose для версионирования схемы.
3. **СУБД не фиксируется этим ADR.** Goose поддерживает несколько СУБД, поэтому выбор инструмента миграций не требует немедленно принимать решение о конкретном хранилище.
4. **Простая операционная модель.** Для проекта достаточно последовательных миграций, таблицы состояния, команд применения, отката, статуса и валидации.
5. **Минимум дополнительной инфраструктуры.** По сравнению с Flyway и Liquibase не требуется вводить вторую языковую runtime-экосистему только ради миграций.
6. **Ниже риск, чем у YDB fork golang-migrate.** Для YDB не нужно зависеть от отдельного fork, пока поддержка YDB в основном `golang-migrate` остаётся непринятой.

### Правила использования

Для принятого решения действуют следующие правила:

- стандартным форматом являются **SQL-миграции**;
- Go-миграции используются только когда требуемое изменение невозможно или неоправданно сложно выразить SQL-миграцией;
- миграции принадлежат модулю и хранятся в существующих `migrations/<module>/`;
- секреты и connection strings не хранятся в migration-файлах;
- конкретные параметры подключения и особенности dialect определяются для выбранной СУБД и окружения отдельно;
- запуск миграций в production должен быть отдельным контролируемым этапом поставки, а не неявным побочным эффектом старта каждого экземпляра приложения;
- версия goose должна быть закреплена в инструментальном окружении проекта после появления Go toolchain.

Выбор стратегии нумерации файлов, политики обязательного `down`, способа блокировки delivery pipeline и точной команды production rollout не входят в этот ADR и должны определяться при проектировании процесса поставки.

## Последствия

Положительные последствия:

- единый migration workflow для всех backend-модулей;
- миграции остаются текстовыми и ревьюятся вместе с изменениями схемы;
- локальная разработка и CI используют тот же Go-native инструмент;
- при выборе YDB не потребуется менять migration framework только из-за отсутствия драйвера;
- сохраняется возможность использовать goose и с другой поддерживаемой СУБД.

Ограничения и риски:

- goose не устраняет различия SQL dialect и транзакционных возможностей разных СУБД;
- миграции после применения должны рассматриваться как неизменяемая история; исправления выполняются новой миграцией;
- rollback DDL может быть невозможен или небезопасен для отдельных изменений, поэтому наличие команды `down` не означает автоматическую обратимость;
- при окончательном выборе СУБД требуется отдельная проверка поведения goose: блокировки, конкурентный запуск, DDL semantics, recovery после частично выполненной миграции и работа в CI;
- при существенном изменении upstream-поддержки goose или выбранной СУБД решение следует пересмотреть.

Перед первым production-применением goose с выбранной СУБД необходимо провести минимальный proof-of-concept: создать схему, применить несколько последовательных миграций, проверить `status` и `validate`, выполнить допустимый rollback и проверить поведение двух конкурентных процессов миграции.
