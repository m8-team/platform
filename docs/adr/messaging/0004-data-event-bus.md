# `ADR-0004`: Шина данных и событий

| Поле | Значение |
| --- | --- |
| Идентификатор | `ADR-0004` |
| Дата | `2026-09-19` |
| Статус | 🟡 **Proposed** |
| Подтверждение согласования | — |

## Контекст

M8 Platform требуется единая [шина событий](*event-bus) для асинхронного обмена между модулями, публикации изменений состояния и подключения внешних потребителей данных.

Шина должна решать следующие задачи:

- доставка доменных и интеграционных событий нескольким независимым потребителям;
- сохранение порядка событий для одной сущности там, где порядок имеет значение;
- повторное чтение и восстановление потребителя после сбоя;
- горизонтальное масштабирование производителей и потребителей;
- контролируемое хранение событий в течение заданного периода;
- наблюдаемость задержки чтения и состояния потребителей;
- возможность атомарно связать изменение операционных данных YDB с публикацией события;
- совместимость с существующими инструментами экосистемы Kafka там, где это требуется;
- единый формат контрактов и правила эволюции схем.

Шина данных не заменяет синхронные вызовы между сервисами, Temporal и основную операционную базу данных.

## Границы решения

Этот ADR определяет транспорт и базовые гарантии для событийной шины.

Шина используется для:

- доменных событий об уже произошедших изменениях состояния;
- интеграционных событий между модулями;
- потоков изменений, предназначенных для нескольких независимых потребителей;
- доставки данных во вторичные представления, поиск, аналитику и другие производные системы.

Шина не используется как:

- замена синхронному API, когда вызывающей стороне нужен немедленный результат;
- замена [Workflow](*workflow) Temporal для многошаговой оркестрации;
- универсальная очередь фоновых заданий;
- система-источник операционного состояния;
- место хранения единственной копии бизнес-данных.

## Решение и обоснование

Предлагается использовать **YDB Topics** как стандартную внутреннюю шину данных и событий M8 Platform.

Нативный YDB Topic SDK является основным способом работы с шиной для сервисов M8. Kafka API YDB используется как интерфейс совместимости для внешних систем, Kafka Connect и инструментов, которым требуется протокол Kafka.

Отдельный кластер Apache Kafka не входит в базовую архитектуру. Его добавление требует отдельного ADR с конкретными требованиями, которые не покрываются YDB Topics.

Причины предложения:

1. **Единая инфраструктурная основа.** YDB уже выбрана основной операционной СУБД в [ADR-0001](../data/0001-primary-database.md), а Topics являются объектами того же пространства YDB.
2. **Атомарность данных и событий.** YDB поддерживает транзакции между строковыми таблицами и топиками, что позволяет в поддерживаемых сценариях фиксировать изменение состояния и публикацию события одной транзакцией.
3. **Подходящая модель доставки.** Топики поддерживают независимых потребителей, смещения, партиционирование и повторное чтение.
4. **Совместимость с Kafka.** Для интеграций доступен Kafka API, поэтому выбор YDB Topics не требует собственного протокола для каждого внешнего инструмента.
5. **Меньше критичной инфраструктуры.** Не требуется отдельный кластер Kafka или NATS только для базового межмодульного обмена событиями.
6. **Преимущество перед NATS в выбранной архитектуре.** NATS с JetStream является полноценной альтернативой для долговечного обмена сообщениями, особенно когда важны низкая задержка, request/reply и независимая от базы данных транспортная плоскость. Для M8 это преимущество не перевешивает необходимость отдельного кластера и отсутствие общей транзакции с операционными таблицами YDB.
7. **Сохранение архитектурной границы.** Прикладной код использует общий слой `internal/platform/messaging/`, поэтому транспортные детали не должны проникать в предметную модель.

## Гарантии доставки и обработка повторов

Сквозной контракт M8 Platform — **доставка как минимум один раз**, даже если конкретный участок транспорта способен предоставить более сильную гарантию.

Это означает:

- каждый обработчик события должен быть идемпотентным;
- событие имеет глобально уникальный `event_id`;
- повторная доставка того же `event_id` не должна повторно изменять бизнес-состояние;
- для критичных потребителей используется [inbox](*inbox) или эквивалентная фиксация обработанных событий;
- смещение потребителя подтверждается только после успешного завершения требуемой обработки;
- ошибка после изменения состояния, но до подтверждения смещения не должна нарушать корректность при повторной доставке;
- гарантия порядка относится только к событиям, направленным в одну логическую последовательность/партицию; глобальный порядок между всеми событиями не обещается.

Для публикации события вместе с изменением строковых таблиц YDB предпочтительна единая транзакция таблица + топик, если она доступна и соответствует сценарию. В остальных случаях используется [транзакционный outbox](*outbox).

## Партиционирование и порядок

Ключ партиционирования выбирается по бизнес-сущности, для которой требуется последовательный порядок событий, например `organization_id`, `project_id` или `resource_id`.

Правила:

- события одной сущности должны попадать в одну логическую последовательность, если потребителю важен их порядок;
- нельзя использовать один постоянный ключ для всего топика, если это создаёт единственную горячую партицию;
- число партиций и автоматическое масштабирование определяются ожидаемой пропускной способностью и измеряются нагрузочными тестами;
- бизнес-логика не должна зависеть от конкретного номера партиции;
- изменение числа партиций не должно менять семантику события.

## Контракты событий

Канонические контракты событий определяются в Protocol Buffers и хранятся в `api/proto/m8/events/v1/`.

Минимальные требования к событию:

- уникальный идентификатор события;
- стабильный тип события;
- версия контракта;
- время возникновения события;
- идентификатор производителя;
- идентификатор сущности или ключ упорядочивания, когда он применим;
- идентификаторы корреляции и причины для трассировки цепочки действий;
- контекст арендатора, организации, рабочего пространства или проекта, когда он необходим потребителю;
- данные события согласно конкретному типу.

Правила эволюции:

- совместимые изменения выполняются внутри текущей версии добавлением новых полей;
- удалённые номера и имена полей Protobuf не переиспользуются;
- несовместимое изменение создаёт новую версию контракта;
- изменения проверяются через `buf lint` и `buf breaking`;
- транспортный формат не должен становиться неявным API: опубликованная схема является источником истины.

Точная структура общего конверта события и правила именования типов определяются отдельной спецификацией до реализации первого производителя.

## Именование и владение

Каждый топик имеет одного владельца на уровне модуля или платформенного компонента.

Владелец отвечает за:

- контракт публикуемых событий;
- политику хранения;
- ключ партиционирования;
- совместимость схем;
- документирование потребителей, для которых потеря данных недопустима;
- метрики публикации, ошибок и задержки чтения.

Автоматическое создание топиков прикладными сервисами в промышленной среде не является стандартным поведением. Топики и их параметры создаются управляемым способом через инфраструктурный или миграционный процесс.

Точная схема имён топиков фиксируется перед реализацией в стандарте обмена сообщениями; ADR не закрепляет строковый формат имени преждевременно.

## Отношение к Temporal

Temporal и шина событий решают разные задачи.

- Temporal управляет состоянием и последовательностью длительного процесса.
- Шина доставляет факты и потоки данных независимым потребителям.
- [Task Queue](*task-queue) Temporal не является общей шиной сообщений.
- Workflow может ожидать внешний сигнал, который формируется адаптером после получения события из шины, но сам Workflow не должен напрямую выполнять сетевое чтение топика.
- Событие не должно использоваться вместо явного шага Workflow только ради уменьшения связанности кода.

## Наблюдаемость и эксплуатация

Для каждого промышленного топика должны быть доступны как минимум:

- скорость публикации и чтения;
- количество ошибок записи и чтения;
- задержка потребителя относительно последнего доступного сообщения;
- размер и возраст накопившихся данных;
- число активных партиций;
- состояние критичных потребителей;
- количество повторных обработок и сообщений, отправленных в карантин или очередь необрабатываемых сообщений, если такой механизм используется.

Длительная задержка важного потребителя должна считаться эксплуатационным сигналом, а не нормальным способом бессрочного хранения событий.

## Последствия

Положительные последствия:

- операционная база и стандартная шина используют одну распределённую платформу;
- для ряда сценариев доступна атомарная фиксация строки YDB и события;
- уменьшается количество обязательных инфраструктурных компонентов;
- внешние системы могут использовать Kafka-совместимый интерфейс;
- появляется единый контракт доставки и идемпотентности для всех модулей;
- каталог `internal/platform/messaging/` получает чёткую архитектурную роль.

Ограничения и риски:

- внутренняя шина становится зависимой от возможностей YDB Topics;
- Kafka API YDB нельзя считать полной заменой любого сценария Apache Kafka без проверки ограничений;
- потребители обязаны корректно переживать повторную доставку;
- неправильный ключ партиционирования может ограничить масштабирование или нарушить ожидаемый порядок;
- важные потребители могут увеличивать объём хранения при длительном отставании;
- для интеграции с системами, требующими специфичные возможности Kafka, может понадобиться отдельный кластер и новый ADR.

## Проверка перед принятием

До перевода ADR в Accepted необходимо провести техническую проверку:

1. создать YDB Topic минимум с двумя потребителями;
2. реализовать производителя и потребителя на Go через нативный YDB SDK;
3. проверить порядок сообщений для одного ключа;
4. проверить повторную доставку после сбоя потребителя до подтверждения смещения;
5. подтвердить идемпотентную обработку через inbox или эквивалентный механизм;
6. проверить транзакцию, изменяющую строковую таблицу YDB и публикующую событие в Topic;
7. проверить чтение того же Topic стандартным Kafka-клиентом;
8. проверить изменение числа партиций или автоматическое увеличение их количества;
9. измерить задержку и пропускную способность на ожидаемом профиле нагрузки;
10. проверить мониторинг отставания потребителя и сценарий длительно неработающего критичного потребителя.

[*at-least-once]: **At-least-once** — модель доставки, при которой сообщение не должно быть потеряно, но при сбоях может быть доставлено повторно.
[*event-bus]: **Event Bus** — инфраструктурный канал публикации и доставки событий нескольким независимым потребителям.
[*inbox]: **Inbox** — шаблон идемпотентного потребления, при котором потребитель сохраняет идентификатор уже обработанного события и не применяет его повторно.
[*outbox]: **Transactional Outbox** — шаблон, при котором бизнес-изменение и запись события фиксируются в одной транзакции базы данных, а публикация в шину выполняется надёжно отдельным процессом.
[*task-queue]: **Task Queue** — механизм Temporal для маршрутизации задач Workflow и Activity к Worker; не является общей очередью бизнес-сообщений.
[*workflow]: **Workflow** — детерминированное описание длительного процесса в Temporal, состояние которого восстанавливается по истории событий.

[*jetstream]: **JetStream** — подсистема NATS для долговременного хранения и повторной доставки сообщений. Добавляет потоки, сохраняемых потребителей, подтверждения обработки, повторное чтение, политики хранения и репликацию поверх базовой модели Core NATS.
