# `ADR-0007`: Идемпотентность и надёжная доставка изменений

| Поле | Значение |
| --- | --- |
| Идентификатор | `ADR-0007` |
| Дата | `2026-09-19` |
| Статус | 🟡 **Proposed** |
| Подтверждение согласования | — |

## Контекст

M8 Platform использует повторные попытки, длительные операции Temporal и доставку событий как минимум один раз. Поэтому повторный запрос, повторное выполнение Activity или повторная доставка события являются нормальным режимом работы, а не исключением.

Нужен единый стандарт:

- идемпотентных команд;
- дедупликации;
- транзакционной публикации событий;
- Inbox/Outbox;
- повторных попыток;
- поведения при частичном сбое.

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения и последствия |
| --- | --- | --- |
| Общий стандарт идемпотентности + YDB transaction + Inbox/Outbox | Предсказуемое поведение всех модулей; можно использовать атомарность YDB Table + Topic; внешние интеграции покрываются Outbox; повторы безопасны на уровне приложения. | Требует общей библиотеки и дисциплины проектирования; хранение ключей идемпотентности и Inbox создаёт дополнительное состояние. |
| Полагаться на гарантии транспорта | Меньше прикладного кода. | Не покрывает повтор клиента, retry Temporal, сбой между внешними системами и повторную доставку; создаёт ложное ощущение exactly-once. |
| Реализовывать отдельно в каждом модуле | Максимальная локальная свобода. | Разные семантики, ошибки и сроки хранения; высокий риск дублирующих побочных эффектов и трудно проверяемых инцидентов. |

## Решение и обоснование

Предлагается считать **идемпотентность прикладным контрактом**, а не свойством транспорта.

M8 Platform не обещает сквозное [exactly-once](*exactly-once). Корректность достигается комбинацией:

- идемпотентных команд;
- атомарных транзакций YDB;
- уникальных идентификаторов событий;
- Inbox для критичных потребителей;
- Outbox для границ, где нет общей транзакции;
- ограниченных и классифицированных повторных попыток.

## Идемпотентность API-команд

Мутация, которую клиент может безопасно повторить, принимает `idempotency_key` или эквивалентный стандартный metadata key, определённый API-стандартом.

Сервис хранит:

- область действия ключа;
- отпечаток значимых входных данных;
- состояние выполнения;
- итоговый результат или ссылку на созданный ресурс/операцию;
- время создания записи.

Повтор того же ключа с тем же запросом возвращает тот же логический результат.

Повтор того же ключа с другими значимыми параметрами отклоняется как конфликт, а не выполняется как новая операция.

Срок хранения ключа определяется классом операции; единый произвольный срок для всей платформы не задаётся этим ADR.

## Транзакционная публикация событий

Если изменение бизнес-состояния находится в YDB и событие публикуется в YDB Topics, предпочтительный путь — одна поддерживаемая транзакция **Table + Topic** согласно [ADR-0004](../messaging/0004-data-event-bus.md).

Это устраняет окно, в котором состояние уже изменено, а событие ещё не опубликовано.

Если атомарная публикация недоступна, используется [Transactional Outbox](*outbox):

1. бизнес-изменение и запись Outbox фиксируются одной транзакцией;
2. отдельный издатель читает неподтверждённые записи;
3. публикация может повторяться;
4. запись помечается опубликованной только после подтверждённой отправки.

Outbox не должен храниться как единственная история аудита.

## Inbox и потребители

Критичный потребитель событий использует [Inbox](*inbox) или эквивалентный механизм дедупликации.

Обработка события и фиксация `event_id` как обработанного по возможности выполняются одной транзакцией с изменением состояния потребителя.

Правила:

- `event_id` глобально уникален;
- повторное событие не повторяет предметный эффект;
- смещение потребителя подтверждается после успешной обработки;
- ошибка после commit, но до подтверждения транспорта приводит к безопасному повтору;
- удаление Inbox-записей возможно только после окна, в котором повторная доставка уже невозможна или безопасно обработана другим способом.

## Идемпотентность Temporal

[Activity](*activity) с внешним побочным эффектом должна быть идемпотентной.

Идемпотентный ключ Activity выводится из устойчивой бизнес-идентичности операции, а не из случайного идентификатора конкретной попытки.

Workflow не должен использовать повторный вызов неидемпотентного внешнего API без отдельного защитного механизма.

Повторные попытки Activity настраиваются с учётом характера ошибки согласно [ADR-0003](../orchestration/0003-workflow-orchestration.md).

## Классификация повторных попыток

Ошибки делятся минимум на:

- временные — повтор допустим;
- постоянные — повтор без изменения запроса не имеет смысла;
- конфликт состояния — требуется повторное чтение или решение вызывающего кода;
- ограничение нагрузки — повтор допускается с задержкой;
- отмена/истечение срока — дальнейший повтор определяется владельцем операции.

Повторные попытки всегда ограничены общим deadline/cancellation budget.

Бесконечный retry loop без внешне наблюдаемого состояния не допускается.

## Внешние системы

Для внешнего API, которое поддерживает собственный idempotency key, M8 передаёт стабильный ключ операции.

Если внешний API идемпотентность не поддерживает, адаптер обязан определить безопасную стратегию:

- предварительное чтение состояния;
- собственный журнал отправок;
- reconciliation;
- компенсация;
- ручная обработка неопределённого результата.

Неопределённый результат внешнего вызова нельзя автоматически считать неуспешным и безусловно повторять.

## Состояние и очистка

Таблицы idempotency, Inbox и Outbox являются техническим состоянием платформы.

Для них должны быть определены:

- владелец;
- первичный ключ;
- срок хранения;
- стратегия очистки;
- метрики объёма и ошибок;
- поведение при недоступности;
- ограничения на размер сохраняемого результата.

## Последствия

Положительные последствия:

- повтор клиента, Temporal и шины не приводит к дублирующим предметным эффектам;
- атомарность YDB используется там, где она действительно доступна;
- Outbox не применяется механически в сценариях, где Table + Topic уже дают общую транзакцию;
- единый подход упрощает общие SDK и interceptors.

Ограничения и риски:

- появляется дополнительное техническое состояние;
- неправильный выбор области idempotency key может объединить разные операции;
- очистка дедупликационных данных требует знания реального окна повторов;
- внешние системы без идемпотентности всё равно требуют предметной стратегии восстановления.

## Проверка перед принятием

1. Реализовать идемпотентную API-команду с повтором одного ключа.
2. Проверить конфликт одинакового ключа с другим payload.
3. Проверить Table + Topic транзакцию YDB.
4. Реализовать Inbox-потребителя и смоделировать сбой после commit до подтверждения сообщения.
5. Реализовать Outbox для фиктивной внешней системы без общей транзакции.
6. Проверить повтор Activity Temporal после неопределённого результата.
7. Добавить метрики повторов, дедупликаций и зависших Outbox-записей.
