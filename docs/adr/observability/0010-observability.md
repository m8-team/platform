# `ADR-0010`: Наблюдаемость платформы

| Поле | Значение |
| --- | --- |
| Идентификатор | `ADR-0010` |
| Дата | `2026-09-19` |
| Статус | 🟡 **Proposed** |
| Подтверждение согласования | — |

## Контекст

M8 Platform состоит из нескольких модулей, YDB, YDB Topics, Temporal, Keycloak и SpiceDB. Без единого стандарта наблюдаемости каждый компонент начнёт по-разному формировать метрики, трассы, логи и идентификаторы корреляции.

Требуется определить:

- стандарт инструментирования;
- способ экспорта телеметрии;
- структурированные логи;
- распространение контекста трассировки через API, события и [Workflow](*workflow);
- целевые системы хранения;
- правила кардинальности и чувствительных данных;
- общие health/readiness сигналы.

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения и последствия |
| --- | --- | --- |
| OpenTelemetry + Collector + Mimir/Loki/Tempo | Открытый стандарт; единый контекст; независимость приложения от систем хранения; готовая интеграция с Go и инфраструктурой; Mimir/Loki/Tempo разделяют метрики, логи и трассы. | Требует эксплуатации Collector и трёх хранилищ; поддержка логов OpenTelemetry в Go развивается отдельно от трасс и метрик. |
| Prometheus SDK + собственные решения для трасс и логов | Простота метрик и зрелость Prometheus. | Три разных способа инструментирования и корреляции; сильнее связывает приложение с конкретными системами хранения. |
| Vendor-specific APM SDK | Быстрый старт и готовый UI. | Привязка к поставщику, стоимость миграции и потеря единого открытого стандарта. |

## Решение и обоснование

Предлагается использовать **OpenTelemetry** как стандарт инструментирования M8 Platform.

Целевой путь:

```text
application
   │
   ├─ traces ─┐
   ├─ metrics ├─> OpenTelemetry Collector
   └─ logs ───┘
                    │
                    ├─> Mimir
                    ├─> Loki
                    └─> Tempo
```

Приложение не должно напрямую зависеть от SDK Mimir, Loki или Tempo.

## Трассировки

Сервисы на Go используют OpenTelemetry API/SDK и стандартные инструментации библиотек, когда они соответствуют фактическим версиям зависимостей.

Span создаются минимум на:

- входящем RPC/HTTP запросе;
- исходящем межсервисном запросе;
- значимой операции YDB;
- публикации/получении сообщения, если библиотека не делает это автоматически;
- [Activity](*activity) и важных границах Workflow Temporal;
- вызове внешнего API.

Не следует создавать отдельный span для каждой небольшой локальной функции.

## Распространение контекста

Основной формат межпроцессного trace context — **W3C Trace Context**.

Контекст передаётся через:

- метаданные Connect/HTTP;
- сообщения YDB Topics;
- Temporal context propagation;
- поддерживаемые внешние вызовы.

Для сообщений контекст трассировки является метаданными конверта/транспорта и не должен менять предметную семантику события.

[Baggage](*baggage) не используется для секретов, токенов, персональных данных или неограниченных пользовательских значений.

## Метрики

Метрики экспортируются через OpenTelemetry и Collector в Mimir.

Правила:

- имена и единицы следуют OpenTelemetry Semantic Conventions там, где они существуют;
- label/attribute с высокой кардинальностью запрещены без явного обоснования;
- `user_id`, `request_id`, `event_id`, `workflow_id` и случайные UUID не используются как metric labels;
- каждый сервис публикует базовые метрики запросов, ошибок, задержки и насыщения ресурсов;
- предметные метрики добавляются только если по ним существует операционное или продуктовое действие.

Численные SLO/SLI не придумываются этим ADR и задаются отдельно для конкретного сервиса.

## Логи

Приложения на Go используют стандартный **`log/slog`** для структурированных логов.

Обязательные общие поля формируются общим logging handler/interceptor, а не вручную в каждом месте.

При наличии активного span лог должен быть коррелируем с `trace_id` и `span_id`.

Логи доставляются в Loki через Collector или инфраструктурный агент. Приложение не использует Loki client API для обычного журналирования.

Уровни:

- debug — диагностическая информация разработки;
- info — значимые нормальные события;
- warn — необычное состояние, не приведшее к отказу операции;
- error — операция завершилась ошибкой или требуется вмешательство.

Одна ошибка не должна без необходимости журналироваться повторно на каждом уровне стека.

## Чувствительные данные

Запрещено писать в телеметрию:

- пароли;
- access/refresh tokens;
- секреты клиентов;
- полные session cookies;
- приватные ключи;
- произвольные содержимое запросов/ответов целиком.

Идентификаторы субъектов и ресурсов допускаются в трассах или логах только если это обосновано диагностикой и соответствует требованиям хранения данных.

## OpenTelemetry Collector

Collector является границей между приложением и системами хранения телеметрию.

Через него централизуются:

- экспорт;
- batch;
- повторные попытки;
- фильтрация;
- преобразование атрибутов;
- удаление запрещённых данных;
- [выборочное сохранение трасс](*sampling), если выбран соответствующий режим;
- маршрутизация по системам хранения.

Конкретная топология Collector определяется при проектировании развёртывания.

## Выборочное сохранение трасс

Выборочное сохранение трасс задаётся конфигурацией и не зашивается в бизнес-код.

Для разработки допускается полный сбор.

Для промышленной среды стратегия должна учитывать:

- объём;
- стоимость;
- сохранение ошибок и редких сценариев;
- возможность выборочного сохранения после завершения трассы в Collector, если она требуется.

Численный процент выборочного сохранения не задаётся без измерений.

## Health и readiness

Каждый серверный процесс предоставляет:

- **liveness** — процесс способен продолжать работу;
- **readiness** — процесс готов принимать полезную нагрузку.

Readiness учитывает только зависимости, без которых экземпляр не может корректно обслуживать запрос.

Кратковременная недоступность необязательного системы хранения телеметрии не должна автоматически делать бизнес-сервис неготовым.

Точка проверки состояния не заменяет метрики и алерты.

## События и Temporal

Для YDB Topics:

- производитель добавляет контекст трассировки в метаданные;
- consumer извлекает context и создаёт новый consumer span;
- повторная доставка сохраняет исходную причинную связь, но каждая попытка обработки может иметь собственный span.

Для Temporal:

- распространение tracing context выполняется через поддерживаемый SDK механизм;
- история Workflow не используется для хранения произвольного объёма телеметрии;
- [Activity](*activity) имеет отдельный [span](*span) и связывается с вызывающим Workflow;
- версионирование и повторное воспроизведение не должны зависеть от недетерминированного телеметрию-кода.

## Корреляция

Кроме trace ID могут существовать предметные идентификаторы:

- `operation_id`;
- `event_id`;
- `workflow_id`;
- идентификатор ресурса.

Они добавляются как атрибуты traces/logs только там, где это помогает расследованию.

Trace ID не используется как предметный идентификатор операции.

## Последствия

Положительные последствия:

- единое инструментирование всех Go-сервисов;
- приложение не связано с конкретным хранилищем телеметрию;
- трассы проходят через синхронные вызовы, события и Temporal;
- структурированные логи коррелируются с трассами;
- кардинальность метрик контролируется общими правилами.

Ограничения и риски:

- Collector и системы хранения наблюдаемости становятся отдельной инфраструктурой;
- слишком подробные spans/logs могут заметно увеличить стоимость хранения;
- неправильное использование baggage может распространить чувствительные данные;
- поддержка OTel Logs в Go должна проверяться по фактической версии; `slog` остаётся стабильным API приложения независимо от способа экспорта.

## Проверка перед принятием

1. Инструментировать один Go-сервис через OTel.
2. Провести trace через Connect вызов двух сервисов.
3. Передать trace context через YDB Topic.
4. Проверить трассу через Temporal Workflow + Activity.
5. Добавить метрики запроса и убедиться в отсутствии меток высокой кардинальности.
6. Связать `slog` запись с trace/span ID.
7. Отправить трассы/метрики/логи через Collector в тестовые системы хранения.
8. Проверить фильтрацию секрета на Collector.
9. Проверить поведение приложения при недоступном Collector.
10. Проверить проверки жизнеспособности и готовности отдельно от доступности системы хранения телеметрии.
