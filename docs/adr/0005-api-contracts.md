# `ADR-0005`: API и межсервисные контракты

| Поле | Значение |
| --- | --- |
| Идентификатор | `ADR-0005` |
| Дата | `2026-09-19` |
| Статус | 🟡 **Proposed** |
| Подтверждение согласования | — |

## Контекст

M8 Platform требуется единый способ описания и вызова API между серверными модулями, веб-консолью и внешними интеграциями. Контракты должны оставаться типизированными, версионируемыми и пригодными для автоматической проверки совместимости.

Исходные API-контракты уже зарезервированы в `api/proto/m8/<module>/v1/`, а контракты событий — в `api/proto/m8/events/v1/`.

Требуется определить:

- единый язык описания контрактов;
- основной транспорт между сервисами;
- доступ из браузера без дублирования отдельного REST API;
- валидацию входных сообщений;
- правила совместимой эволюции;
- единый подход к ошибкам;
- представление длительных операций;
- распространение метаданных запроса, аутентификации и трассировки.

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения и последствия |
| --- | --- | --- |
| Protocol Buffers + Connect | Один типизированный контракт; генерация клиентов; поддержка обычного HTTP, Connect, gRPC и gRPC-Web; удобная работа из браузера; совместимость с экосистемой Protobuf; проверка через Buf. | Требует генерации кода и дисциплины совместимости; внешним клиентам без Protobuf может потребоваться отдельный адаптер или опубликованная документация. |
| Чистый gRPC | Зрелый двоичный протокол, потоковые вызовы, богатая экосистема и строгие контракты. | Браузеру обычно требуется gRPC-Web или прокси; обычная HTTP-диагностика менее удобна; отдельный REST-слой быстро приводит к дублированию контрактов. |
| REST + OpenAPI | Широко распространён; прост для произвольных HTTP-клиентов; хорошо поддерживается инфраструктурой API Gateway. | При ручном проектировании появляется второй источник типов; сложнее обеспечить единообразие между внутренними и внешними API; потоковые сценарии требуют отдельных решений. |
| GraphQL | Гибкие выборки и развитый клиентский инструментарий для UI. | Не решает задачу межсервисных контрактов как основной транспорт; добавляет отдельную схему и модель ошибок; усложняет эксплуатацию при использовании вместе с Protobuf. |

## Решение и обоснование

Предлагается использовать **Protocol Buffers** как единственный источник схем API и **Connect** как основной прикладной транспорт.

Правила:

1. Все публичные контракты модулей определяются только в `api/proto/`.
2. Серверные обработчики на Go используют Connect.
3. Сервер должен сохранять совместимость с gRPC там, где это поддерживает используемая версия Connect и требуется инфраструктуре.
4. Веб-клиенты используют Connect/Web; отдельный вручную поддерживаемый REST API для тех же методов не создаётся.
5. Для интеграций, которым требуется обычный REST/JSON контракт, создаётся отдельный граничный адаптер только при наличии конкретного требования.

## Структура и именование

Пакеты Protobuf имеют версию в имени:

```text
m8.resources.v1
m8.identity.v1
m8.authentication.v1
m8.access.v1
m8.events.v1
```

Файлы используют `lower_snake_case.proto`. Имена сообщений, сервисов и методов следуют единым правилам Protobuf и Buf.

Каждый [RPC](*rpc) имеет собственные сообщения запроса и ответа. Повторное использование одного и того же запроса между разными методами не является стандартом.

## Валидация

Для входных данных используется **Protovalidate**.

Правила:

- ограничения описываются в схеме Protobuf, а не дублируются вручную в каждом обработчике;
- обязательность, формат, диапазоны и ограничения коллекций задаются там, где они являются частью контракта;
- предметные правила, требующие чтения состояния или сложной логики, остаются в предметном слое;
- проверка схем выполняется через `buf lint`;
- после появления конфигурации Buf версия зависимостей фиксируется в `buf.lock`.

## Совместимость и версии

Совместимые изменения выполняются внутри текущего пакета `v1`.

К совместимым относятся, если семантика не меняется:

- добавление нового поля;
- добавление нового значения перечисления;
- добавление нового метода;
- пометка старого элемента устаревшим.

При удалении поля его номер и имя резервируются.

Несовместимые изменения требуют новой версии пакета, например `v2`.

В CI выполняется `buf breaking` относительно основной ветки. Точный набор правил Buf фиксируется в конфигурации проекта до публикации первого стабильного API.

## Ошибки

Транспортная ошибка содержит:

- канонический код ошибки Connect/gRPC;
- безопасное для клиента сообщение;
- типизированные Protobuf details, если клиенту требуется машинно обрабатываемая причина;
- идентификатор трассировки или корреляции через общие метаданные, а не через предметное сообщение.

Внутренние ошибки, стек вызовов и секреты клиенту не возвращаются.

Предметные ошибки должны иметь стабильную машинно обрабатываемую семантику. HTTP-статус или текст ошибки не являются единственным контрактом.

## Длительные операции

Операция, которая не должна удерживать синхронный запрос до завершения, возвращает ресурс длительной операции по модели [LRO](*lro).

Правила:

- идентификатор операции стабилен и пригоден для повторного чтения;
- состояние операции хранится независимо от клиентского соединения;
- выполнение может быть реализовано через Temporal согласно [ADR-0003](0003-workflow-orchestration.md);
- API не раскрывает внутренние идентификаторы исполнения Temporal как публичный контракт;
- отмена предоставляется только если операция действительно поддерживает безопасную отмену.

Точная Protobuf-схема операции определяется до реализации первого метода такого типа.

## Межсервисные вызовы

Синхронный вызов применяется, когда вызывающей стороне нужен результат для продолжения текущей операции.

Асинхронные факты и интеграционные события передаются через шину согласно [ADR-0004](0004-data-event-bus.md).

Сервис не должен выбирать событие только для сокрытия обязательной синхронной зависимости и не должен выбирать RPC для широковещательной доставки факта множеству независимых потребителей.

## Метаданные и перехватчики

Общий набор перехватчиков должен обеспечивать:

- аутентификацию и передачу подтверждённого субъекта;
- авторизацию в предусмотренных точках;
- ограничение времени выполнения и отмену;
- трассировку и метрики;
- единое журналирование;
- преобразование внутренних ошибок в стандартную модель API;
- идемпотентность для методов, для которых она требуется согласно [ADR-0007](0007-idempotency-and-delivery.md).

Предметная логика не должна зависеть от конкретных HTTP-заголовков Connect.

## Последствия

Положительные последствия:

- единый источник контрактов для Go и веб-клиентов;
- совместимость с gRPC без отдельного набора схем;
- автоматическая проверка несовместимых изменений;
- единая валидация и модель ошибок;
- возможность использовать обычный HTTP/JSON для диагностики Connect API;
- меньше ручного дублирования REST-контрактов.

Ограничения и риски:

- требуется настроить Buf, генерацию кода и проверку совместимости до первого API;
- разработчикам необходимо соблюдать правила эволюции Protobuf;
- нестандартные внешние интеграции могут потребовать отдельные граничные адаптеры;
- модель длительных операций требует отдельной спецификации до реализации первого LRO.

## Проверка перед принятием

1. Настроить минимальный `buf.yaml` и генерацию Go-кода.
2. Создать тестовый унарный RPC на Connect.
3. Вызвать его Connect-клиентом и gRPC-клиентом.
4. Проверить вызов из браузерного клиента.
5. Добавить Protovalidate и подтвердить единообразное преобразование ошибки валидации.
6. Проверить `buf lint` и `buf breaking`.
7. Реализовать один типизированный error detail.
8. Проверить распространение trace context через Connect interceptor.
9. Описать минимальную схему LRO и проверить её совместимость с Temporal.
