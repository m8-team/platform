# Архитектурные решения

ADR фиксирует значимое решение: границы ответственности, совместимость, владение данными, устойчивые межмодульные соглашения или выбор технологии с существенными последствиями. Для каждой локальной детали реализации ADR не нужен.

Принятые архитектурные решения перечислены в реестре ниже. Наличие ADR со статусом Proposed не считается согласованием архитектуры.

## Создание и изменение

Используйте [шаблон](../specs/_templates/adr.md). Путь записи — `docs/adr/<number>-<short-name>.md`, идентификатор — `ADR-<number>`; выберите следующий свободный номер и не переиспользуйте его.

Новый ADR начинается со статуса Proposed. Accepted присваивается после явного согласования командой, со ссылкой на его подтверждение. Rejected означает отклонённое предложение; Deprecated — решение, выведенное из применения; Superseded — заменённое новым ADR.

Существенный пересмотр принятого ADR оформляется новым ADR со ссылкой на предыдущий. В предыдущем указываются статус Superseded и ссылка на замену, без удаления контекста и обоснования старого решения. Редакционные исправления допустимы на месте, история остаётся в Git.

Указывайте фактическую дату записи или решения и связи со спецификациями, PR и другими ADR. Не добавляйте вымышленные подтверждения согласования.
