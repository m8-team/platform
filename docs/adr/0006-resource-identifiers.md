# `ADR-0006`: Идентификаторы и имена ресурсов

| Поле | Значение |
| --- | --- |
| Идентификатор | `ADR-0006` |
| Дата | `2026-09-19` |
| Статус | 🟡 **Proposed** |
| Подтверждение согласования | — |

## Контекст

Resource Manager должен задать единый способ идентификации организаций, рабочих пространств, проектов и будущих ресурсов платформы. Без общего стандарта модули могут начать использовать несовместимые ID, имена, правила родительства и версии.

Решение должно отделять:

- стабильную идентичность ресурса;
- человекочитаемое или иерархическое имя;
- физический первичный ключ YDB;
- родительскую связь;
- версию для оптимистичной блокировки;
- метаданные жизненного цикла.

## Рассмотренные варианты

| Вариант | Преимущества | Ограничения и последствия |
| --- | --- | --- |
| [UUIDv7](*uuid) + иерархическое имя ресурса | Стандартный 128-битный идентификатор; генерируется на клиенте/сервисе без центрального счётчика; удобен для журналов и сортировки по времени создания; имя ресурса отражает иерархию. | UUIDv7 частично монотонен и не должен бездумно использоваться первым компонентом распределяющего первичного ключа YDB. |
| [UUIDv4](*uuid) | Простая случайная генерация; хорошее распределение; широко поддерживается. | Не содержит временной упорядоченности; сложнее визуально анализировать последовательность создания. |
| [ULID](*ulid) | Лексикографическая сортировка и удобное текстовое представление. | Не является UUID; меньше стандартной поддержки в API и БД-инструментах; также имеет временно монотонную часть. |
| Централизованный числовой ID | Компактность и привычная сортировка. | Требует генератора последовательностей; создаёт лишнюю зависимость и плохо соответствует распределённой архитектуре YDB. |

## Решение и обоснование

Предлагается использовать **UUIDv7** как стандартный стабильный ID новых ресурсов M8 Platform.

ID:

- генерируется до записи ресурса;
- не переиспользуется;
- не кодирует арендатора, тип ресурса или бизнес-смысл;
- остаётся неизменным на всём жизненном цикле;
- передаётся в Protobuf как строка UUID, пока не появится отдельный общий тип.

Формат ID не определяет физическую форму первичного ключа YDB.

## Имена ресурсов

Для API вводится каноническое имя ресурса.

Предлагаемый вид:

```text
organizations/{organization_id}
organizations/{organization_id}/workspaces/{workspace_id}
organizations/{organization_id}/workspaces/{workspace_id}/projects/{project_id}
```

Поле `name` содержит полное каноническое имя, а `id` — только стабильный UUID ресурса.

Для вложенного ресурса дополнительно используется `parent` с каноническим именем родителя.

На первом этапе перемещение рабочего пространства между организациями и проекта между рабочими пространствами не считается базовой операцией. Если такая возможность потребуется, её семантика и влияние на `name` оформляются отдельной спецификацией или ADR.

## Общие метаданные ресурса

Для управляемых ресурсов используется единый набор понятий:

- `id` — стабильный UUIDv7;
- `name` — каноническое имя ресурса;
- `parent` — имя родителя, если ресурс вложенный;
- `display_name` — изменяемое отображаемое имя, если требуется;
- `labels` — пользовательские метки ограниченного размера;
- `create_time` — время создания;
- `update_time` — время последнего изменения;
- `version` — монотонная версия для оптимистичной блокировки.

Конкретный ресурс может не иметь `display_name`, `labels` или `parent`, если они не имеют предметного смысла.

## Оптимистичная блокировка

Мутации, для которых важно обнаруживать потерянные обновления, принимают ожидаемую `version`.

При успешном изменении версия увеличивается владельцем ресурса.

Клиент не генерирует новую версию самостоятельно.

Конфликт версии возвращается через стандартную модель ошибок [ADR-0005](0005-api-contracts.md).

## YDB и физические ключи

UUIDv7 не должен автоматически становиться единственным первым компонентом первичного ключа YDB.

Согласно [ADR-0001](0001-primary-database.md), физический первичный ключ проектируется под реальные сценарии доступа и распределение нагрузки.

Допустимые подходы включают:

- родительский ID + ID ресурса;
- хеш-префикс + ID;
- другой составной ключ, если он обоснован запросами.

API-идентичность ресурса и физическая схема хранения остаются раздельными решениями.

## Удаление и жизненный цикл

Единая платформа не вводит обязательный soft delete для всех ресурсов.

Каждый тип ресурса должен явно определить:

- разрешено ли удаление;
- является ли оно немедленным или отложенным;
- возможно ли восстановление;
- что происходит с дочерними ресурсами;
- когда прекращается авторизация и внешние интеграции.

Если ресурс поддерживает отложенное удаление, в его контракт может быть добавлено `delete_time` или предметное состояние жизненного цикла.

Удалённый ID не переиспользуется.

## Ссылки между модулями

Модуль хранит ID или каноническое имя внешнего ресурса, но не копирует его внутреннее состояние без необходимости.

Наличие ссылки не даёт права читать таблицы другого модуля напрямую.

Проверка существования, жизненного цикла и прав выполняется через контракт владельца ресурса или через согласованный событийный поток.

## Последствия

Положительные последствия:

- единый формат ID по всей платформе;
- отсутствие центрального генератора идентификаторов;
- канонические имена отражают иерархию ресурсов;
- API-модель не привязана к физической схеме YDB;
- единый механизм защиты от потерянных обновлений.

Ограничения и риски:

- UUIDv7 нельзя использовать как оправдание монотонного первого ключа YDB;
- иерархическое имя усложняет будущий перенос ресурса между родителями;
- ограничения labels, display name и других общих полей ещё нужно зафиксировать в API-стандарте;
- модель арендатора остаётся отдельным архитектурным решением и не выводится автоматически из Organization/Workspace/Project.

## Проверка перед принятием

1. Проверить генерацию UUIDv7 в выбранной Go-библиотеке без глобального состояния.
2. Создать Protobuf-модель Organization/Workspace/Project с общими полями.
3. Проверить парсинг и валидацию канонических имён.
4. Смоделировать оптимистичный конфликт по `version`.
5. Проверить схему YDB с UUIDv7 при нескольких вариантах первичного ключа.
6. Убедиться, что API не раскрывает физический ключ таблицы.
7. Описать поведение удаления хотя бы для одного ресурса.
