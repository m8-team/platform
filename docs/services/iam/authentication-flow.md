# Authentication: взаимодействие с API

## Последовательность

1. Доверенный клиент (например, BFF) вызывает `Create` со своей аутентификацией,
   `client_id`, входным `subject`, `start_context` и UUID `request_id`.
   Пользователь на этом этапе ещё не обязан иметь access token. Учётные данные
   сервисного клиента нельзя передавать браузеру.
2. Клиент читает LRO через сервис операций под исходной идентичностью вызывающего.
   Create завершается после подготовки аутентификации и challenge, без ожидания
   ответа пользователя. Успешный ответ содержит `authentication` и `interaction`.
3. Для Get, SelectChallenge, ResendChallenge, VerifyChallenge и Cancel клиент
   передаёт свою аутентификацию и заголовок
   `x-m8-authentication-interaction-token: <interaction_token>`.
   В gRPC используется metadata с тем же именем. Сервер проверяет срок действия
   токена и привязку к вызывающему, `client_id` и `authentication_id`.
4. SelectChallenge принимает `available_challenges[].challenge_id` из актуального
   snapshot. После выбора `current_challenge.id` совпадает с выбранным ID.
   Устаревший или недоступный вариант отклоняется без смены текущего challenge.
5. Каждая LRO завершается после выполнения своей команды. Текущее состояние после
   push approval, callback или истечения времени читается через Get. Клиент
   прекращает polling при AUTHENTICATED, FAILED, CANCELLED или EXPIRED.

Сервис операций должен проверять владельца при каждом чтении, включая повторное
чтение завершённого Create: его результат содержит секрет. Сам UUID операции не
даёт права чтения. Interaction token не включается в snapshot, события или логи;
он возвращается только в результате Create. Его срок должен покрывать возможность
получить терминальный snapshot; сервер определяет и документирует окно чтения
после завершения аутентификации, при этом терминальные ресурсы не изменяются.

## Повторные запросы

Каждая логическая мутация получает новый UUID `request_id`. При сетевом повторе
клиент использует тот же ключ и payload. Сервер после авторизации возвращает
исходную LRO, не отправляя повторно OTP и не расходуя ещё одну попытку проверки.
Область ключа: вызывающий, клиент, RPC и целевой ресурс. Для Create область цели
задаётся `client_id`. Другой payload с тем же ключом возвращает ALREADY_EXISTS.
Ключ хранится минимум 24 часа и не меньше срока жизни аутентификации. После
истечения токена повтор мутации отклоняется; получить ранее выданную LRO можно
через авторизованный сервис операций.

Поля ключей оставлены необязательными для старых клиентов. Без ключа гарантия
дедупликации отсутствует. Ключи не заменяют лимиты отправки OTP и проверки ответов.

## Входные данные и публичный snapshot

`start_context` содержит недоверенные hints. Сервер самостоятельно определяет
состояние сессии, достигнутый AAL, trusted device, сетевые и риск-факторы и
проверяет допустимость запрошенных ресурсов и параметров провайдера.
`options.provider_id` разрешено опускать, например для password; если поле задано,
оно должно быть UUID разрешённого провайдера.

`public_subject.masked_identifier` — маска введённого идентификатора, например
`a***@example.com`. Она не должна зависеть от наличия учётной записи. Исходный
`subject` не возвращается, включая user ID. Секреты и введённые идентификаторы
не должны попадать в логи. Публичные ошибки также не должны раскрывать наличие
учётной записи; внутренние причины остаются на стороне сервера.

## Миграция клиентов

Номера и типы старых полей сохранены. Вместо `CreateRequest.context` (поле 3)
нужно отправлять `start_context` (поле 5). Старый context помечен deprecated;
его передача отклоняется валидацией, включая совместную передачу двух контекстов.
Это намеренное изменение поведения, хотя wire-схема остаётся совместимой.

Вместо `Authentication.subject` (поле 3) следует читать `public_subject` (поле 17).
Старое поле deprecated и запрещено в публичном snapshot правилом валидации.
Сервер должен применять проверку и безопасное преобразование перед выдачей ответа.

Пример тела Create (идентификаторы приведены для иллюстрации):

```json
{
  "clientId": "d9e31b5a-05c0-40e8-94d4-8ddc984073c5",
  "subject": {"email": "alice@example.com"},
  "startContext": {"request": {"locale": "ru"}},
  "options": {"methodId": "password"},
  "requestId": "f043af0b-9c36-4b75-852c-a5ac099cd061"
}
```

Этот документ определяет требования контракта. Проверки прав, токенов,
идемпотентности, rate limiting и выполнение Get требуют серверной реализации.
