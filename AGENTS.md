# Инструкции для ИИ

Эти правила действуют во всём репозитории. Учитывайте также инструкции в затрагиваемых подкаталогах.

## Перед изменениями

- Изучите существующие файлы, инструкции и рабочее дерево. Сохраняйте пользовательские изменения и содержание существующих документов.
- Прочитайте [общие принципы](docs/principles.md), [границы модулей](docs/architecture/module-boundaries.md), описание нужного модуля в `docs/specs/<module>/module.md` и затрагиваемую спецификацию.
- Если спецификации ещё нет, руководствуйтесь [циклом SDD](docs/development/sdd-workflow.md) и соразмерностью процесса.
- Перед изменением поведения обновите требования. Не расширяйте задачу без основания.
- Не превращайте предположения в подтверждённые требования: явно обозначайте открытые вопросы и предложения.

## Использование установленных skills

Применение подходящих skills обязательно при проектировании, реализации, отладке и ревью. Не ждите отдельного напоминания пользователя. Выбирайте skills по содержанию задачи и их условиям применения; для несвязанных задач загружать все skills не требуется.

### Выбор и чтение

- В начале задачи проверьте доступные `.agents/skills/*/SKILL.md` и их поля `name` / `description`. [skills-lock.json](skills-lock.json) содержит сведения об установленных источниках; инструкции берите из фактического `SKILL.md`.
- Учитывайте метаданные вызова и возможности среды. У `temporal-ops` задано `disable-model-invocation: true`: в средах, поддерживающих этот флаг, нужен явный вызов пользователем. Если подходящий skill требует такого вызова, сообщите об этом; не обходите ограничение и не заявляйте автоматическое применение.
- Перед соответствующим этапом работы прочитайте полностью выбранный `SKILL.md`, затем обязательные и относящиеся к задаче references по его указаниям. Относительные пути внутри skill разрешайте от его каталога.
- Кратко сообщите, какие skills применяете и для чего. Если задача расширилась, повторно оцените применимость остальных skills.
- Таблица ниже помогает выбрать текущие skills, но не заменяет их инструкции. Новые установленные skills также подлежат проверке на применимость; при изменении состава поддерживайте таблицу актуальной.

### Текущие skills

| Skill | Когда применять |
| --- | --- |
| [gravity-ui](.agents/skills/gravity-ui/SKILL.md) | Проектирование, реализация, исправление и ревью UI на Gravity UI: компоненты, формы, таблицы, навигация, темы и стили. Проверяйте фактически установленные пакеты и версии перед использованием API. |
| [temporal-developer](.agents/skills/temporal-developer/SKILL.md) | Разработка и отладка Temporal workflows, activities, workers и SDK-интеграций; determinism, retries, signals, queries, updates, versioning и replay. Для Go читайте предусмотренные skill Go references. |

Это отдельный этап ревью, дополняющий temporal-developer. |
| [temporal-workertuning](.agents/skills/temporal-workertuning/SKILL.md) | Настройка производительности и масштабирования Temporal workers: slots, pollers, cache, latency, ресурсы и метрики. |

Настройка Helm, Kubernetes и СУБД вне области этого skill. Выбирайте инструкции для фактической модели развёртывания; Cloud-specific команды не переносите на self-hosted. |

Например, для изменения workflow используйте temporal-developer для реализации и temporal-workflow-design-critic для ревью; workertuning и ops добавляйте при наличии задач по производительности или эксплуатации.

### Связь с SDD и проверками

- При уточнении требований и планировании используйте skills для выявления ограничений, рисков и открытых вопросов. Они не заменяют спецификацию и не являются подтверждением согласования технологии или архитектуры.
- В `plan.md`, если он нужен, либо в связанном issue укажите выбранные skills и существенные ограничения, влияющие на решение и проверки. Не копируйте содержимое skills в спецификации.
- При реализации выполняйте применимые инструкции skills с учётом фактических версий SDK, библиотек и окружения. Установка skill сама по себе не означает, что соответствующая библиотека или сервис уже установлены либо выбраны проектом.
- Перед завершением выполните предусмотренные выбранными skills применимые проверки. В итоговом отчёте укажите использованные skills, фактические результаты и ограничения. Чтение skill не считается выполнением проверки.
- Если подходящий skill или обязательный reference недоступен, явно укажите это и продолжайте независимую часть задачи. Не заявляйте применение непрочитанного skill и не выдумывайте его инструкции.

### Актуальность и обновление skills

- Проверяйте установленные skills не реже одного раза в неделю. Плановая проверка настроена отдельной задачей ChatGPT «Обновления skills M8» по понедельникам утром (Europe/Vienna), целевая ветка — `new`. Сам `AGENTS.md` не запускает фоновые проверки.
- Дополнительно проверяйте применимые skills при обновлении используемых SDK/библиотек, обнаружении устаревшей инструкции или по запросу пользователя. Не обновляйте skills незаметно посреди реализации функции.
- Состав и upstream-источники берите из актуального `skills-lock.json`; проверяйте полные каталоги, включая references, scripts и assets. Одного поля `version` в frontmatter или даты upstream-коммита недостаточно. Фиксируйте точный upstream commit SHA.
- Подготавливайте обновления в отдельной ветке от актуальной `new` и отдельном PR. Если PR с теми же обновлениями уже существует, актуализируйте его без перезаписи чужих изменений; не создавайте дубликаты. Автоматическое слияние не выполняется.
- Используйте project-scoped обновление официальным менеджером [vercel-labs/skills](https://github.com/vercel-labs/skills): `npx skills update -p -y`. Перед запуском сверяйте поддержку параметров с документацией или `--help` выбранной версии CLI; версию CLI указывайте в отчёте. Работайте в отдельном чистом checkout, чтобы проверить diff до переноса изменений.
- Обновляйте содержимое skills и lock-файл согласованно. Не выдумывайте `computedHash`, не меняйте источники автоматически и не затрагивайте глобальные skills или зависимости приложения. Сохраняйте локальные адаптации; конфликты обозначайте явно.
- Перед PR проверьте diff, frontmatter, обязательные ресурсы и относительные ссылки. Оцените изменения условий вызова, разрешений, скриптов и требований к версиям зависимостей; проверьте согласованность с правилами SDD и принятыми ADR. Добавление скрипта upstream не означает необходимости его запуска.
- В PR укажите изменённые skills, upstream-ревизии, существенные изменения, выполненные проверки и ограничения. При необходимости обновите таблицу применения выше. Несовместимости оформляйте как замечания в draft PR.
- Результат успешной проверки без обновлений сохраняется в истории плановой задачи; уведомление не требуется. При появлении обновлений сообщайте ссылку на PR. Недоступность источника или инструмента — ошибка проверки, а не подтверждение актуальности; сообщайте конкретное препятствие.

### Противоречия и границы

- Соблюдайте системные инструкции, правила среды и явные указания пользователя. Skills не предоставляют дополнительных разрешений на внешние действия.
- Применяйте skills в рамках `AGENTS.md`, согласованных требований и ADR проекта. Если рекомендация расходится с ними или с фактической версией зависимости, явно зафиксируйте противоречие и его влияние; не меняйте согласованное поведение молча.
- Разрешайте обычные технические вопросы по доступным исходникам, документации установленной версии и существующим решениям. Если противоречие требует нового продуктового или архитектурного решения, оформите открытый вопрос или предложение по циклу SDD.

## Во время работы

- Поддерживайте согласованность спецификаций, контрактов, кода и проверок в одном PR.
- Храните общие правила централизованно; используйте ссылки. Исходные API-контракты хранятся только в `api/proto/`, без копий в спецификациях.
- Не считайте все разделы шаблонов обязательными. Разделы «по ситуации» заполняйте при применимости; существенное исключение кратко обоснуйте.
- Не требуйте полноценного SDD-процесса для редакционных правок и простых исправлений. Для небольшой задачи достаточно issue; изменение поведения должно оставаться отражённым в требованиях.
- Создавайте ADR для значимых архитектурных решений, а не для каждой локальной детали реализации. Не присваивайте ADR статус Accepted от имени команды без подтверждения согласования.
- Приоритеты, сроки и ответственных ведите в трекере, не дублируйте в Markdown.
- Документацию пишите на русском в формате YFM для Diplodoc; имена файлов, каталогов и технические идентификаторы — на английском. Соблюдайте [правила сборки и навигации](docs/development/diplodoc.md): новые страницы добавляйте в `docs/toc.yaml`, после изменений выполняйте `pnpm --dir docs run build`. Исходные SDD-документы остаются единым источником; сгенерированный сайт не редактируется и не коммитится.
- Размещайте unit-тесты Go рядом с исходниками. Не добавляйте тесты ради проверки наличия каталогов.
- Не добавляйте секреты, фиктивные реализации или вымышленные результаты проверок.

## Завершение работы

- Следуйте [Definition of Done](docs/development/definition-of-done.md).
- Не помечайте задачу завершённой без подтверждения критериев завершения.
- Указывайте фактически выполненные проверки, их результаты и ограничения. Невыполненные проверки обозначайте явно.
- Различайте согласованное целевое поведение (Accepted) и реализованное, проверенное поведение (Implemented); см. [версионирование](docs/development/versioning.md).
- Учитывайте текущий этап каркаса: не создавайте бизнес-логику, API-методы, миграции, инфраструктурные ресурсы или зависимости без соответствующей задачи.
