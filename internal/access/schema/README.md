# M8 Access — SpiceDB Schema v1

**Status:**
candidate;
publish
only
after
running
`zed schema validate`
against
a
pinned
SpiceDB
version
(>=
1.40),
graph
fixture
checks,
explicit
security
approval
and
rollout
plan.
The
`.zed`
is
**not
auto-deployed**
by
this
PR.

## Invariants and mapping

-

The
graph
is
a
*projection*,
not
the
source
of
truth
for
organizations,
workspaces,
roles,
bindings
or
grants.
Resource
Manager
owns
resource
hierarchy/tenant
binding;
Access
owns
roles,
bindings,
grants
and
permissions.

-

Every
resource
and
subject
`object_id`
is
`<tenant-uuid>/<base64url(unpadded original id)>`,
as
encoded
by
`adapters/spicedb/mapping.go`.
Tenant
trust
comes
from
verified
identity
and
authoritative
resource
tenant,
not
raw
request
fields.

-

Only
`organization`,
`workspace`,
`environment`
and
`workload_service`
are
supported
resource
types.
`project`
is
intentionally
excluded
pending
ADR-0001.

-

Published
`PermissionDefinition.GraphPermission`
must
be
one
of
`view`,
`edit`,
`manage`,
`delete`,
`deploy`
as
applicable
to
the
resource
type.
The
projection
writes
to
the
**relation**
(`viewer`,
`editor`,
`manager`,
`deleter`,
`deployer`),
not
to
a
computed
permission.

-

M8
`Role`
remains
an
authoritative
permission
set
in
Access
storage;
each
RoleBinding
is
projected
as
a
unique
`access_binding:<binding_id>`
node
with
a
`holder`
relation.
The
role's
permissions
become
resource
edges
such
as
`workspace:<scope_id>#viewer@access_binding:<binding_id>#holder`.
Role
changes
require
fan-out
reprojection
of
**every**
binding
using
old/new
role
snapshots.

-

Each
M8
AccessGrant
has
its
own
`access_grant:<grant_id>`
node;
this
prevents
two
independent
grants
of
an
identical
permission
to
the
same
subject
from
overwriting
each
other.
`APPROVED`
stages
resource
edges
only.
`ACTIVE`
adds
`access_grant:<grant_id>#holder@user:<user_id>`
with
`optionalExpiresAt`
equal
to
`expires_at`.
This
deliberately
separates
approval
and
effective
access.
`REVOKED`/
`EXPIRED`
remove
only
that
grant's
relationships.

-

`access_binding`
and
`access_grant`
support
`user`
and
`service_account`
principals
only
in
v1.
No
implicit
OrganizationGroup
membership,
inheritance,
or
support
for
arbitrary
subject
types.

-

No
grant
with
MFA,
active-case,
active-assignment,
service-agreement
or
policy
conditions
is
projected
as
an
active
permission:
the
projector
fails
closed
until
a
trusted
caveat/context
evaluation
path
is
implemented.

## Activation / revocation sequence

1.

Validate
tenant
and
authoritative
resource
ownership.
Persist
the
AccessGrant
state
change
and
corresponding
outbox
event
in
the
authoritative
Access
store
with
idempotency
and
revision
preconditions.

2.

On
`APPROVED`,
stage
resource→grant
edges.
Store
the
completed
SpiceDB
`writtenAt`
ZedToken
with
a
durable
**projection
checkpoint**;
only
then
allow
`AccessGrant.Activate(... projectionRef ...)`
to
transition
to
`ACTIVE`.

3.

After
the
committed
`ACTIVE`
event,
add
the
expiring
grant→subject
edge.
Consumers
cannot
interpret
`ACTIVE`
alone
as
authorization.
All
runtime
access
still
goes
through
the
PDP.

4.

On
`REVOKED`/
`EXPIRED`,
enforce
an
immediate
deny
barrier
against
stale
positive
decisions;
remove
that
grant's
resource
and
holder
edges
as
an
atomic
SpiceDB
write;
store
the
ZedToken
and
advance
the
source
watermark
after
durable
checkpoint.
A
SpiceDB
ZedToken
alone
is
not
an
upstream
source
revision.

5.

Replay
each
aggregate
serially
(same
tenant +
aggregate
ID),
load
the
exact
last-applied
source
snapshot/model
revision,
and
only
then
apply
deltas.
The
projection
port
does
not
implement
storage
or
Kafka
offset
claiming;
those
are
required
in
a
separate
worker
and
must
not
be
skipped
in
production.

## Expiration caveat

SpiceDB
expiration
requires
`use expiration`
and
an
expiration-enabled
relation;
`optionalExpiresAt`
is
set
only
on
the
grant
holder
edge.
Time
is
measured
against
the
SpiceDB
datastore
clock.
Cache
freshness
and
clock
skew
must
meet
the
approved
access
revocation
window;
for
critical
checks,
use
a
sufficiently
fresh
snapshot
and
fail
closed
if
not
available.

## Validation and release

-

Domain/projection
tests:
`go test ./internal/access/domain ./internal/access/app/projection ./internal/access/adapters/spicedb`.

-

Before
schema
rollout:
`zed schema validate --file internal/access/schema/m8.zed`
using
the
approved
CLI
flags/version.
Run
fixture
assertions
for
overlapping
grants,
a
staged
grant,
expiry,
revocation
and
cross-tenant
isolation
against
live
SpiceDB.

-

Publish
schema
before
enabling
the
new
projection
writer.
Do
not
remove
old
relations
until
all
readers
and
source
projections
have
migrated.
Capture
the
deployed
schema
revision/model
marker
separately
from
ZedTokens.
